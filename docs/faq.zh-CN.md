# 常见问题

*本文从 README（常见问题）移来，之后在这里更新。*

*条目里按名字指到 README 的「磁盘空间」一节，那段文字现在在 [hardware.zh-CN.md](hardware.zh-CN.md#磁盘空间)。*

**启动自检有一行未生效。** 每一行下方即为对应的处理步骤；未生效的项还会在页面顶部
留一条提示，待机和直播中都在，直到之后的自检通过。最常见的两种情形是
`banned_terms.txt` 为空（此时不会发出任何报警），以及降噪模型未下载完整
（删除 `models/bd.rnnn` 后重新开始，程序会重新下载）。每次启动都会重新自检，
问题解决后下一次即恢复正常。通过的项表示该能力已被实际执行，而非仅配置正确。

**一键更新提示有内容阻断。** 提示中会列出受影响的文件，并给出包含项目路径的
完整命令及「复制」按钮。v0.10.4 之前的版本无法自行修复——修复随更新送达，而被
阻断的正是更新。这些旧版本的提示让你执行 `git pull`，不要照做：它会把主分支上
还没发布的改动一起装上。改为在项目目录中执行一次下面两条命令，把 `vX.Y.Z` 换成
[发布页](https://github.com/EM917/tiktok-live-translator/releases/latest)上最新版本的标签：

```bash
git fetch --tags --force
git merge --ff-only vX.Y.Z
```

现在的版本在提示里给的命令也是这两步：装的是那个发布版本，不带它之后的改动。

**性能下降、音频开始积压。** 先查看 `ollama ps`。Ollama 在模型最后一次使用后
将其保留在显存中 30 分钟，因此切换翻译档位时旧模型此前会继续驻留；与 Whisper
large-v3 叠加后足以耗尽 16–18 GB 机器的内存并引发换页，表现为识别变慢与积压提示。
现在未使用的档位会在启动时卸载。旧版本可执行 `ollama stop <模型名>` 立即释放。

**浏览器中可以观看，但程序拿不到流地址。** 这种直播 yt-dlp 有时会回答「未开播」，
所以程序不会到此为止：它按[抗故障](fault-tolerance.zh-CN.md)里列的各层依次尝试，只有 TikTok
自己说直播已结束才判定下播。在 Safari 或 Chrome 中登录 TikTok 对部分直播间有帮助，
但通常并非必需，也无需导出任何文件；cookie 仅在本机与 TikTok 之间使用。可用
`--cookies-browser safari` 指定浏览器，或通过 `--cookies cookies.txt` 提供 cookie。
如需长期只读取某一个浏览器，在 `settings.json` 中设置
`"cookies_browser_only": "safari"`；显式给出的 `--cookies-browser` 优先于该设置。

<a id="zh-browser-login"></a>**启动自检的「浏览器登录态」一行显示「系统拒绝读取」。** macOS 不允许其它程序读取浏览器的
数据目录，除非该程序有「完全磁盘访问权限」。要加进去的**不是这个 .app**：.app 只是一段
启动脚本，随后交给 Python 解释器运行，系统把权限登记在解释器文件的路径上（2026-09-17
在 macOS 27 上实测：TCC 日志里是 `identifier_type=Path` 加一个 `python3.x` 的路径，
从未出现过本程序的 bundle）。点「开始翻译」后窗口顶部那条提示、报错信息，以及没有哪个浏览器读到
TikTok 登录时自检的这一行，都会给出本机要加的路径。照三步做：1. 打开「系统设置」→「隐私与安全性」→
「完全磁盘访问权限」；2. 点「+」，在选文件的窗口里按 ⌘⇧G，粘贴路径后回车、点「打开」，再把它的开关
打开，给出几个路径就各做一遍（列表里显示的名字是 `python3.x`，不是本程序的名字）；3. 按 ⌘Q 完全退出
程序再打开。只有从终端启动程序时（比如双击 Start.command），第 2 步要把「终端」
（`/System/Applications/Utilities/Terminal.app`）也照这样加进去，系统要「终端」退出并重新打开时照做，
再启动程序。做完第 2 步可以先点提示或这一行上的「我加好了，再查一次」：程序当场只看一次 cookie 库读不读得到
（不解密），说现在能不能读取，还是要做第 3 步；提示挂着时，从系统设置切回程序窗口也会自动查一次。
两个启动器都用建运行环境（`.venv`）的那个 Python 启动程序，只要它还在、版本没变；
所以装上或升级别的 Python（比如 Homebrew 装别的软件时顺带装上新的 `python@3.x`），路径不会变。
那个 Python 自己升级、挪走或被卸掉，或者运行环境重建之后，路径才会变，届时这一行会给出新的路径。
路径没变时，也会出现列表里已经有这一项、开关也开着，这一行却仍然显示「系统拒绝读取」的情况：
这时先选中它点「−」删掉，再做一次第 2 步。这项权限给的是 Python 解释器，不只是本程序：用这个 Python
运行的任何脚本都能读取这台电脑上受保护的数据，比如邮件、信息和 Safari 的数据。不再需要借用浏览器里的
TikTok 登录时，在同一个列表里把这一项的开关关掉。
这一项只影响 TikTok
要求登录才给流地址的直播间；自检只看 cookie 库能否读取和登录 cookie 的名字（每个浏览器
个人资料都看），不解密、不弹钥匙串对话框。解析失败时审计里记的是代码：`blocked_by_system`、
`no_browser_data`、`no_tiktok_cookie`、`not_logged_in`、`cannot_decrypt`、`keychain_wait`。
`cannot_decrypt` 指库里有 TikTok 的 cookie 名字、解密后却没有对应的值：再点一次「开始翻译」，
屏幕上如果出现「钥匙串」对话框（要访问「Chrome Safe Storage」），输入这台电脑的登录密码后点
「始终允许」。

<a id="zh-code-4003110"></a>**提示「TikTok 不把这个直播间的流地址给程序（代码 4003110）」。** 这是 TikTok 的
通用拒绝码，返回体里没有原因，程序也不替它编一个。下结论之前先跑内置的检查：

```bash
python3 tools/diagnose_room.py @主播名 --history-only   # 只看本机日志，不发请求
python3 tools/diagnose_room.py @主播名                  # 再做同一分钟的配对检查
```

它先用零请求按主播聚合你自己的 `logs/session-*.jsonl`——这个直播间在本机到底
出过字幕没有、出过的是哪些——再在同一分钟里用同一条接口探目标房间和一个最近
成功过的对照房间（共 4 次请求，不开浏览器）。结论只区分「只有这个房间被拒」和
「本机什么都拿不到」，不贴原因标签。期间可以把直播间链接和浏览器里的 `.flv`
地址一起粘进来（见上文[「抗故障」](fault-tolerance.zh-CN.md)），一次约两周有效。

**首次启动长时间停留在下载识别模型。** 模型正从 Hugging Face 下载
（large-v3 约 3 GB），进度显示在页面上，仅首次需要。

**全部翻译失败，字幕只剩原文。** Google 免费接口（没装本地模型时 `auto` 用的就是它）
按 IP 限流，持续使用会返回 429。程序会暂停请求两分钟后自动恢复，并在页面给出提示；
语音识别不受影响。长时间使用建议装上本地 Hy-MT2 模型，或者点「停止」后在「设置 → 翻译引擎」里
换一个引擎（直播中设置分组是隐藏的）。断网或 Ollama 未运行会产生相同现象。

**状态显示「直播中」但长时间没有字幕。** 通常属正常情况：主播播放音乐或未讲话
期间，静音与低置信度片段会被主动丢弃。音量一直低于识别门限的音频根本不送去识别；
连续 2 分钟的音频都是这样、或者 5 分钟里送去识别的不到六成时，页面顶部会有提示，写出收到了多少、
送去了多少（[详见](fault-tolerance.zh-CN.md#跟上直播流)）。若主播明确在讲话且始终无输出，可尝试
`--denoise off` 或更换模型尺寸。

**合上笔记本或切换网络后字幕中断。** 直播流中断时程序会自动重连。刚收到过音频时，先用
原来的流地址重连，这一步只连视频服务器，不碰直播页和 TikTok 接口；这样连上还是没有音频
（或者原地址明显已经拉不动），再重新查流地址。一直没有音频时间隔逐次拉长（2 秒，然后 4、
8、16 秒，最长 30 秒；连续 30 分钟没有音频后是 60 秒），收到任何音频就从头算。为少向
TikTok 发请求，任意一小时里最多查 26 次流地址，等直播恢复时复查房间状态也算在里面；到了
上限就继续用原来的流地址重连，状态行会说多久之后再查。连续 30 分钟没有音频后，最多每
15 分钟查一次。本机连不上 TikTok 期间只等待、不去查，最多等 30 分钟。

直播间链接不会因为一直没有音频就放弃。只有这几种情况会停止监听：TikTok 说直播已结束
（状态 4；电脑睡过的话先复查一次）、TikTok 接口约 10 分钟内一直没有返回在播状态、连不上
TikTok 超过 30 分钟、连续 6 次查流地址都失败。粘贴的流地址连续 2 次连接都没有音频就停止。
状态行会写这是本场第几次中断（「本场第 7 次中断」）。

两条提示说明实际听到了多少。2 分钟没收到直播音频时，页面顶部出现「已 N 分钟没收到直播
音频」，收到音频就撤掉。近 5 分钟收到的直播音频不到 70% 时出现「近 5 分钟只收到 N% 的
直播音频」，回到 85% 以上才撤；底部大字幕下面同时有一个「近 5 分钟收到 N%」的小角标。
有的音频要等程序关掉卡住的连接时才晚到，这些照样送去识别、做违禁词检测；它们不算实时
收到，提示里会写其中多少已经检测过。详见[保住直播流](fault-tolerance.zh-CN.md#保住直播流)。

想在某一次运行里退回原来的重连规则（每次重连都重新查流地址、连续 6 次连接都没有音频就
停止、状态行写「第 N/M 次」），用 `TLT_RECONNECT_V2=0` 启动程序。这时 FLV 流也回到由 ffmpeg
自己重连。上面两条提示、卡住时停止拉流的时间上限和审计记录不受影响。`TLT_FFMPEG_LEGACY=1` 是另一个
开关：它让 ffmpeg 退回原来的参数，不改重连规则。两个开关合在一起怎么算，见[保住直播流](fault-tolerance.zh-CN.md#保住直播流)。

**默认关着的开关。** `TLT_ASR_TOKEN_CAP=on`（每段最多解码 112 个 token）、`TLT_ASR_MASK_LANGS=on`
（语言检测时就从「主播语言」列表里挑语言，列表外的段不再整段再解码一遍）和 `TLT_LOW_BITRATE_STREAM=1`（TikTok
没给纯音频档时拿画质最低的那档）默认都关着，启动程序时设了才打开。每一个都可能改变识别出的内容或出字幕
的快慢，所以打开之前先看它的评测结果；现在还一次都没评过，先别打开。各自改了什么、评测要看什么，见
[默认关着的开关](fault-tolerance.zh-CN.md#默认关着的开关)。

<a id="zh-captions-in"></a>**把「字幕译成」改成 English，界面却没变成英文。** 顶栏的「字幕译成」菜单只管
字幕译成哪种语言：简体中文、繁体中文、英语、西班牙语。界面语言是另一项设置，在首页的
「设置 → 界面语言 · Language」（见[界面语言](interface-language.zh-CN.md)）。以前的版本存过别的
字幕语言，或者用 `--target` 加别的语言代码启动时，字幕照旧译成那种语言，菜单里多出这一项，
直到你改选四种之一。选了西班牙语时，识别成西语的段不送翻译、原样显示；英语那几段
照常译成西语。

**直播中换一个主播。** 点顶栏的「换主播」，粘贴新主播的直播间地址或 @用户名，或者从
「最近的直播间」里选（当前主播标着「当前」，不能选），再选好本场品牌。这时按钮会变成
「再点一次：改听 @新主播（停止监听 @当前主播）」，6 秒内点它确认。当前这一场随即停止，
用同样的主播语言开始新的一场，并重新读取各词表和违禁词表。新主播开口之前两边都没有
字幕，字幕历史里会插一条分隔线标出切换的位置。「停止」则不同：它结束监听、回到首页。

**识别跟不上直播流。** 改用较小的模型（`--model small`）或 `--beam 1`。Apple
Silicon 机器请确认自检显示的后端为 `mlx` 而非 `ct2`——CPU 路径仅勉强达到实时，
长时间运行会产生积压。

**8 GB 内存的 Mac 上运行迟缓。** Apple Silicon 默认使用 `large-v3`（约 3 GB）。
内存受限时可改用 `--model large-v3-turbo` 或 `--model small`。

**限制 MLX 为复用而保留的缓冲内存（Apple Silicon）。** 2026-09-17 在一台 18 GB 的
M3 Pro 上实测（macOS 27、mlx 0.32.1、Whisper large-v3、fp16、进程已运行 28 分钟）：
`footprint` 显示监听进程占用 7.5 GB，其中 6948 MB 为 "IOAccelerator (graphics)"，
即 Metal 缓冲，其余部分合计不到 0.5 GB；模型权重约 3.1 GB。这类缓冲属于 wired
统一内存，既不能压缩也不能换出。当时整机已使用 10 GB 交换空间，同一时段按需加载的
7B 翻译模型加载耗时 42–60 秒。MLX 会把释放的缓冲留在缓存中以便复用，不设上限时缓存随音频段长度的种类增多而增长。
程序默认把该缓存的上限设为 256 MB。这个数值来自同一天停播后的实测
（`tools/bench_mlx_cache.py`，同一段音频逐段配对）：相对不设上限，识别耗时变化
−0.5%，95% 置信区间 −2.2% 至 +1.0%，与两次不设上限的对照之间的波动相当；显卡缓冲
由 4305 MB 降至 3220 MB。完全不保留缓存时识别耗时增加约 6%。可通过环境变量
`TLT_MLX_CACHE_MB`，或 `settings.json` 中的 `"mlx_cache_limit_mb"` 改动（环境变量
优先）；取值为非负整数，单位 MB，`0` 表示不保留缓存，`off` 表示不设上限。
该设置仅对 `mlx` 后端生效，在识别模型加载时读取，修改后需重新
启动程序。实际生效的数值记录在会话日志的 `asr_config` 中；`asr_memory` 记录（模型
就绪时一条，此后每 5 分钟一条）给出 MLX 的在用、缓存与峰值内存读数。

**背景音乐中的人声被识别为主播讲话。** RNNoise 对器乐的抑制效果良好，但对歌曲中
的**人声**只能部分抑制。置信度过滤可滤除大部分此类片段，偶有漏网属预期范围。

<a id="zh-recognition-audio"></a>**「磁盘空间」里的「识别音频片段」是什么？** 程序会把一部分段前后
几秒的直播音频存进 `logs/asr-evidence/`，留给人事后回头听、核对识别得对不对：识别风险规则标记的段、
违禁词命中的段（警示关闭时也存）、在这个窗口里点过「重译」的字幕（手机上点的不算），以及每 50 段里
抽 1 段没被标记的当对照。每段一个 WAV（本段加前 2 秒、后 1 秒），`index.jsonl` 里一行记着当时的
识别输出。存下来的是直播的混音，同场的人、连麦的人和背景音乐都在里面。这些音频只在这台电脑上：
程序不上传、不发给任何接口、不放进导出，`logs/` 也不进 git。整个目录超过 1 GB（1024 MB）、
6000 个文件或 14 天时，从最旧的一场删起；当前这一场不删。这一步在每场开始时做，所以过了 14 天的片段要到下一场
开始时才删。「设置 > 磁盘空间」里能看到它，也能删掉。存音频不在识别的路径上，写不进去只在终端打一行
警告。要关掉，在 `settings.json` 里写 `"asr_evidence": false`，或者设环境变量 `TLT_ASR_EVIDENCE=0`。
关掉只是不再存新的；已经存下的，要么等某一场开始时按上限删掉，要么在「磁盘空间」里自己删。上限是 `asr_evidence_max_mb`（默认 1024）、
`asr_evidence_max_files`（默认 6000）、`asr_evidence_days`（默认 14）、`asr_evidence_ring_sec`（内存里
留多少秒最近的音频，默认 600）和 `asr_evidence_control_every`（默认 50，`0` 表示不存对照段），每场
开始时读一次。想少占些空间，就在 `settings.json` 里写小一点的数，比如 `"asr_evidence_max_mb": 300`。

<a id="zh-recognition-risk"></a>**识别风险记录，以及怎么关掉。** 审计日志里每一段都有一个 `asr`
对象，里面只有数字和简短的代码：段长、怎么切的、有声帧的占比、每有声秒的词数、解码器给的平均对数
概率、无人声概率和压缩比，以及风险规则 v1 的标记（`low_conf`、`nan_lp`、`few_words`、`loop`；
`outro_only` 记进审计、也存音频片段，但不挂角标；`relabel` 只记录）。阈值冻结为第 1 版，写在 `asr_config` 里；`session_end.asr_risk`
是这一场的计数。有标记说明这一段像是识别出了大问题；没有标记不代表识别对了。违禁词匹配仍然最先在
识别出的原始文字上跑，不用这里的任何东西。在 `settings.json` 里写 `"asr_uncertain_chip": true`
（默认关，每场开始时读一次）后，命中前四条规则的字幕会在卡片和底部大字幕下面挂一个「语音识别不确定，
建议查看原文」的角标，鼠标停在上面能看到具体看到了什么。字幕文字一个字不改，也不给翻译引擎加任何话；
报警、手机同看页和浮窗都不显示这个角标。要把风险标记、识别音频片段和角标一起关掉，用
`TLT_ASR_SAFEGUARDS=off` 启动程序，数字照样记进审计日志。要回退代码，撤掉加入 `app/asr_risk.py`、
`app/asr_evidence.py` 和角标的那几个提交；别的代码不读这些新的审计键，删掉 `logs/asr-evidence/`
对程序没有影响。

**界面地址不是 8765。** 8765 被占用时程序会顺延至 8766–8774 中的空闲端口，
并在终端里说明。这条只讲控制面：手机同看用自己的端口，端口空着时重启后沿用同一个，
贴出去的二维码不会失效，见下一条。

<a id="zh-phone-viewing"></a>**同事能用手机看吗？** 可以。点顶栏的手机图标（窗口宽于 1100 像素时旁边写着「手机同看」；
待机、直播中都在），在弹出的面板里点「开始同看」。第一次打开时 macOS 或 Windows 防火墙
可能会询问是否允许传入的网络连接，选「允许」。手机连上和这台电脑同一个 Wi-Fi，
扫二维码或手工输入面板上的地址即可；手机端只能看字幕和报警，
不能操作本程序——开始、停止、切引擎、改设置都不行。手机页按那台手机自己的语言显示，
页面底部可以切换。最多同时 12 台手机在看。
链接里带着一把钥匙，当密码看待：发给谁，谁就能看到字幕和报警。手机打开链接时，页面先把钥匙
存进那台手机的浏览器，再从地址栏里去掉；之后在那台手机上刷新或再打开这个页面，用的是存下的钥匙。
浏览器自己的历史记录里还留不留扫码时那个带钥匙的地址，没有核实。这台电脑的局域网地址和手机同看的
端口都没变时，墙上的二维码一直有效，再扫一次就再存一遍。其中一个变了，面板上会换成新的二维码，
要扫这个新的：之前贴出去的二维码指向原来的地址，手机上存下的钥匙也是跟着原来的地址走的。浏览器
存不进去时（页面存完会读回来核对；比如在浏览器设置里关掉了网站数据），钥匙留在地址栏里，页面照旧
能用。点「换一个链接」会让当前在看的手机全部断开，每台手机都会丢掉旧钥匙，
要扫新的二维码。

iPhone 上有两种情况，都没在 iPhone 上试过。钥匙从地址栏去掉之后才加到主屏幕的图标，它自己的地址里
没有钥匙；iOS 如果把这个图标当网页 App 打开，图标用的是自己的一份存储，重新扫码只会存进 Safari，
图标还是拿不到钥匙：这时请在 Safari 里扫码、在 Safari 里看。地址里还带着 `#k=` 时加的图标照旧能用。
另外，一个网站 7 天没打开过，Safari 可能会清掉它存下的数据，页面就没有钥匙了，重新扫一次二维码就好。

手机打不开时，程序这边只知道没有
连接进来，可以依次试：确认手机连的是同一个 Wi-Fi；换面板列表里另一个地址手工
输入；在本机浏览器打开同一个链接，确认服务本身在跑。局域网上的地址是 `http://`，
不是安全上下文，所以没有系统通知、没有屏幕常亮，页面切到后台或手机锁屏后，
提示音可能会停掉。v1 只支持同一个局域网内访问，不支持跨网络。每条字幕还带一个
「重译」按钮，点了会让中控电脑用最强的模型重新翻这一句（当前引擎是 Claude 时是
Claude Sonnet 5.5，否则是最强的本地模型）；这个按钮按手机做了
限速（两次点击至少隔 3 秒，每分钟最多 10 次），一台手机连点也不会堆积任务、拖慢
中控电脑。所有手机合起来还共用一个上限：每分钟最多 20 次（一下子最多 5 次），断开重连也不会重置，
超出的点击不执行。识别落后时，手机上点的重译先不执行，手机上的按钮显示「重译失败，可再试」。每条报警带一个 ✕，另有「清除已看过的报警」一次性隐藏当前显示的全部——
这两个操作只在点击的这台手机上生效，中控电脑的报警面板和审计记录都不受影响，
也不会发送任何内容到服务端。

<a id="zh-floating-window"></a>**能把字幕一直放在别的软件上面吗？** 可以，在程序自己的窗口里。监听期间点顶栏的
「浮窗」（窗口不到 1400 像素宽时去掉图标、只显示这两个字；顶栏放不下这两个字的时候，比如「报警开」标签亮着，或者窗口很窄，只显示图标），会打开一个深色小窗，始终在别的软件上面。里面是最新一条字幕（译文大字，原文在下面；上面一行是和主窗口一样的状态标签，这一句超过 15 秒会写「约 N 秒前」，
重连时写「连接中…」）和最近几条弹幕与它们的译文（最多五条，窗口拉高才看得全），被弹幕留意标成红色或琥珀色的弹幕标记照旧。它只显示：
没有报警，也不会向程序发任何东西。可以拖动、拉大缩小，位置和大小记在 `settings.json` 的
`float_window` 里，下次打开沿用，除非那个位置已经不在任何屏幕上。第一次打开时，Mac 会把它放在主窗口所在屏幕的右下角附近，别的系统由系统自己摆。点它自己的关闭按钮、点「停止」、
关闭主窗口，它都会关掉。直播结束或监听出错停下时，它不关，写「直播已结束」或「监听已停止」（详情见主窗口），
下面只有一个按钮「回到主窗口」，点了把主窗口提到最前；Mac 上程序不在前台时，Dock 图标还会跳一下。只有程序在自己的窗口里运行时才有「浮窗」按钮，加了 `--browser` 就没有。
（在浏览器里打开一个正在运行的应用窗口的地址，会看到这个按钮，点它会在应用里打开浮窗。）

<a id="zh-viewer-comments"></a>**观众弹幕。** 评论由程序自己通过 TikTokLive 获取，这需要 Python 3.10 或更新版本；
没装的话，程序启动时、或者开播要用弹幕时会自动装上（[做法说明](fault-tolerance.zh-CN.md#保住直播流)）。
一般免登录，TikTok 要求登录时会借用浏览器里的 TikTok 登录态重试一次。
弹幕只在当前翻译引擎是本地模型（Hy-MT2 1.8B 或 TranslateGemma）或 Claude 时
翻译，用 Google、DeepL、OpenAI 或 7B 时面板只显示原文。用 Claude 时，弹幕由 Claude Haiku 5.5
通过另一条连接翻译，并且先让字幕翻译，所以那条连接暂停不会拖慢字幕。弹幕翻译只用于显示，不进报警链路。连接签名经第三方服务，
见[隐私与使用边界](../README.md#zh-privacy)。
审计日志里 `session_end.comment_fields` 只用数字记下有多少条弹幕带了各个账号字段，眼下也记账号等级、
徽章这些候选字段（`level_has`、`level_hist`、`level_kinds`）；这些界面上都不显示。

**导出字幕。** 每一场都边听边存在程序文件夹里的 `transcripts` 文件夹：每条字幕和它的译文
（「重译」的结果会替换最初那条译文），以及每条观众弹幕和它的译文、昵称。文件是一行一行写下的，
程序崩溃最多丢掉正在写的那一行。它和审计日志是两个文件，审计日志里没有弹幕内容；程序不会上传
字幕记录，也不会删除它。

页面保留最近 300 条字幕和 100 条弹幕，刷新或重连后程序把同样的内容放回来。点顶栏的「清空字幕」和弹幕栏的「清空弹幕」会连
程序里存着的一起清掉，清掉的字幕和弹幕刷新后不会再回来；字幕记录和审计日志不受影响。两颗按钮都要点两次：
第一次点下去按钮变成「再点确认」，6 秒内再点一次才清空。之后才连上的手机，
字幕和弹幕各只看到最近 100 条。往上翻着看时，「回到最新」按钮会写出翻上去之后又来了几条新字幕（弹幕栏里
是几条新弹幕）。

要导出，先停止监听，打开「设置 → 字幕记录」，点「导出最近一场」。程序会在记录文件旁边生成三个文件并
打开文件夹：Markdown（字幕和弹幕分成两节，各自写原文和译文）；CSV，列是 `time`、`kind`、`user`、
`original`、`translation`，UTF-8 带 BOM，Excel 打开中文不会乱码，字幕和弹幕按时间排在一起；SRT 字幕文件
（译文在上、原文在下，时间从这一场开始算起，每条显示到下一条出现为止，最长 8 秒）。CSV 里以 `=`、`+`、`-`、
`@` 开头的单元格前面会补一个撇号，避免 Excel 把观众的弹幕当公式执行。直播中设置分组是隐藏的，导出的是最近
一场已经结束、并且记到了内容的直播。开始监听后拿不到流地址、或者马上停止的那几次，只会留下一个只有文件头的
文件：它还在文件夹里，但「导出最近一场」和设置里的场数都不算它。「打开文件夹」只打开 `transcripts` 文件夹，不导出。

**关闭黑色命令行窗口。** Windows 上该窗口即翻译程序本身，关闭它等同于退出程序；
macOS 上关闭程序窗口即可退出（直播中会先问一句），若通过 `Start.command` 启动则关闭
终端窗口或按 Ctrl-C。

**公司电脑无法安装或空间不足。** 首次安装约需 6 GB，并需访问 PyPI、Hugging Face、
ollama.com 与 GitHub，各部分体积见「磁盘空间」一节。企业安全策略常会阻断上述访问。
